# Обновление DSM и Pinology

[English](../en/updates.md) · [Документация](../README.md)

DSM можно обновлять через её веб-интерфейс, в том числе скачивая обновление по
сети. Pinology и эмулятор обновляются отдельно на хосте. Это экспериментальная
система: **перед любым из этих обновлений сделайте холодный checkpoint** и храните
независимую резервную копию важных файлов.

## Какие версии DSM могут загрузиться?

В исходниках Pinology v0.1.0 разрешены следующие загрузочные файлы для каждой модели:

| Версия DSM | DS223 | DS423 |
| --- | --- | --- |
| 7.2.2-72806 | Профиль начальной установки | Профиль начальной установки; экспериментальный |
| 7.2.2-72806 Update 9 | Flash распознаётся | Flash распознаётся; экспериментальный |
| 7.4.1-90080 | Загрузочный профиль распознаётся | Загрузочный профиль распознаётся; экспериментальный |

Update 9 содержит загрузочные файлы flash из Update 4, поэтому внутреннее имя
профиля — `7.2.2-72806-flash4`. Это **не** означает, что проверен каждый номер
Update. Хеши загрузочных файлов не определяют все установленные службы и пакеты;
после обновления смотрите фактическую версию в DSM.

Источник истины — [профили установки](../../kernel/stock-board/profiles.py) и
[профили загрузки из flash](../../kernel/stock-board/boot_from_flash.py). У DS223
и DS423 разные хеши ramdisk/DTB даже при одинаковом ядре. Появление новой версии
в DSM не подтверждает совместимость с Pinology. Распознавание загрузочного
профиля не гарантирует исправность всех служб, пакетов и вариантов хоста.

## Перед обновлением

1. Проверьте модель, текущую версию DSM и точную целевую сборку, включая номер
   Update. Прочитайте примечания к выпуску и требования к промежуточным версиям.
   Каждый промежуточный запуск тоже должен поддерживаться; не принуждайте DSM
   принимать неподходящий PAT и не обходите неподдерживаемый промежуточный этап.
2. Убедитесь, что нужный профиль есть именно в запускаемом runtime. Обновление
   Git-каталога само по себе не обновляет уже собранный Mac-комплект или Docker-образ.
   При необходимости сначала выполните [обновление Pinology](#обновление-pinology).
3. В **Панель управления → Обновление и восстановление → Обновление DSM →
   Настройки обновления** выберите уведомления/ручную установку вместо установки
   без подтверждения. Эта предосторожность для Pinology отличается от обычной
   рекомендации для поддерживаемого NAS; не выставляйте устаревший тестовый гость
   в интернет.
4. Выключите систему **из DSM** и дождитесь завершения оболочки/контейнера.
   Создайте checkpoint в новом каталоге; его родитель должен уже существовать:

```sh
./pinology backup instances/nas instances/nas-before-update
./pinology start instances/nas
```

Для DS423 добавляйте `--experimental-ds423` ко всем командам `start` в этой
инструкции. На CM4/Pi 4 добавляйте `--experimental-gicv2`; при необходимости — оба
флага. Сохраняйте свои параметры HTTP/SMB-портов. Исходный checkpoint должен
оставаться выключенным и нетронутым. Экспорт настроек DSM не заменяет копию диска
и flash.

## Установка обновления из DSM

1. Откройте DSM по <http://127.0.0.1:5000/> или своему порту/SSH-туннелю.
   Перейдите в **Панель управления → Обновление и восстановление → Обновление DSM**.
2. Если предложена проверенная целевая версия, скачайте её и следуйте указаниям
   установки. Если она не предлагается, используйте **Обновление DSM вручную**
   с официальным PAT для **той же модели и точной поддерживаемой версии**.
   Исходный `nas.media/boot.pat` — образ начальной установки, а не автоматически
   подходящий файл обновления. Ознакомьтесь с лицензионными условиями и примите их
   самостоятельно. См. [инструкцию Synology](https://kb.synology.com/index.php/en-us/DSM/help/DSM/AdminCenter/system_dsmupdate?version=7).
3. Оставьте оболочку, Docker engine (на Linux) и хост работающими. Не закрывайте
   терминал, не останавливайте контейнер и не отключайте питание во время установки
   и перезагрузки. Потеря связи с браузером ожидаема, но не доказывает завершение.

При перезапуске Pinology читает обновлённую постоянную flash и проверяет ядро,
ramdisk и DTB. Подтверждённый guest reset обрабатывается автоматически с учётом
[лимита перезапусков](usage.md#сеть-и-перезапуск). Если оболочка завершилась или
отказалась принимать профиль, изучите её вывод и журналы экземпляра; не запускайте
бесконечные повторы и не отключайте проверки. Для поддерживаемого обновления DSM
не нужно повторять `init` или вручную заменять загрузочные файлы.

## Проверка результата

После возвращения DSM выполните `./pinology status instances/nas`, затем проверьте
в DSM целевую версию, состояние пула/тома, общие файлы, доступ по SMB, сеть и нужные
вам пакеты. Запущенный QEMU или HTTP 200 сами по себе не доказывают успех.
Дождитесь завершения миграций пакетов/индексации и разберите обнаруженные ошибки.
Храните checkpoint до прохождения этих проверок и следующей штатной перезагрузки.

Манифест экземпляра может по-прежнему указывать исходную установочную сборку.
Это не отчёт о текущей версии установленной DSM: не редактируйте `instance.json`
только ради совпадения номера с веб-интерфейсом.

## Если обновление не удалось

Сохраните неудачно обновлённый экземпляр и его журналы для диагностики. До запуска
восстановленной копии убедитесь, что старый экземпляр больше не работает; не
используйте занятые им диск или порты. Если выключение зависло, обратитесь к
[диагностике](troubleshooting.md), а не считайте принудительную остановку контейнера
штатным выключением DSM.

Восстановите целиком checkpoint **до обновления** в другой новый каталог:

```sh
./pinology backup instances/nas-before-update instances/nas-restored
./pinology start instances/nas-restored
```

Так возвращаются согласованные диск, flash и манифест. Изменений после checkpoint
в копии не будет. Не откатывайте отдельно ядро/PAT, не смешивайте старую flash с
обновлённым диском, не перезаписывайте неудачный экземпляр и не подменяйте хеши для
допуска неизвестной прошивки. Держите независимую копию на другом носителе.

## Обновление Pinology

Это обновляет оболочку/эмулятор, **а не DSM**. Выключите DSM и сделайте checkpoint.
Сохраните прежние исходники и собранный runtime, затем получите нужный релиз
Pinology в отдельный каталог. Прочитайте его примечания и выполните там
`./pinology doctor` и `./pinology build`. На Mac появится новый `dist/pinology-macos`
без перезаписи комплекта в прежнем каталоге. На Linux сохраните существующий образ
до сборки: она повторно использует тег `pinology:local`.

```sh
# Только Linux; выберите ещё не занятый резервный тег:
docker image tag pinology:local pinology:before-update
```

Запускайте CLI из нового каталога с **абсолютным путём к существующему экземпляру**;
не инициализируйте и не конвертируйте его заново. По возможности сначала проверяйте
холодный клон при выключенном оригинале. Для возврата Linux-runtime сначала
выключите гостя, верните образу `pinology:before-update` тег `pinology:local` и
используйте прежние исходники. На Mac используйте прежний каталог и комплект.
Если новый runtime или DSM несовместимо изменили состояние экземпляра, восстановите
и checkpoint: замена исполняемых файлов не отменяет эти изменения.
